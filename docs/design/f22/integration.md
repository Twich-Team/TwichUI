# F22 integration and frame attachment

Design research only, 2026-11-23. No runtime change or compatibility certification is implied. Findings below are **source-verified**, with native combat, taint, appearance and event delivery **not tested**. See [detection](detection.md) for the meaning and limits of the signals.

## Source identity and confidence

The inspected provider is [EllesmereUI commit `8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5`](https://github.com/EllesmereGaming/EllesmereUI/tree/8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5). Unit Frames and Raid & Party Frames `.toc` files declare **9.9.1**, support Interface **16001**, and depend on the parent EllesmereUI addon. `EllesmereUI_ClientGate.lua` recognizes Forever interfaces 16000–19999. The repository's prior [Execute Range investigation](../execute-range.md) pins the same provider. Its custom license reserves rights: inspect reference code; implement original adapter code, do not vendor its implementation.

The API reference is [Forever commit `734f065329cff4992835b01a84f210a297db91b6`](https://github.com/Gethe/wow-ui-source/commit/734f065329cff4992835b01a84f210a297db91b6), **1.60.1 (71037)**. The available local Forever checkout was older (`bebcb6bf309cf41b41bd74f8ca651e6a105b2676`, 1.60.1 / 70938); decisive files were read from the newer immutable commit, without modifying that checkout. No installed EllesmereUI or live client was available. Paths below are within those pinned upstream repositories, not asserted installed paths. Source excerpts were retrieved to disposable scratch outside the repository; none is shipped.

## Event architecture comparison

| Choice | Fit and costs | Decision |
|---|---|---|
| A. Ellesmere-native propagation | Use original TwichUI-owned native containers/slots through the inspected AuraKit API. Engine evaluates tokens/candidates and owns secret-driven visibility. One native consumer per bound frame still has cost, but no TwichUI parallel Lua aura cache is necessary. It cannot report secret slot occupancy for arbitrary cross-rule arbitration. | Preferred for predicates native containers can express. This is native presentation propagation, not a fictional aura callback. An actual supported provider callback, if subsequently supplied, could improve lifecycle discovery; it must be verified first. |
| B. TwichUI dispatcher | `!!!TwichUI/Core.lua:232`, `R:On` / `R:Off`, multiplexes ordinary events and passes payload only. A module can add one `UNIT_AURA` listener, filter to its active token set, coalesce readable deltas and remove its listener on disable. It remains a global event listener and receives unrelated aura traffic. Forever marks `UNIT_AURA` restricted/secret in relevant contexts. | Useful only for a separately justified readable-data evaluator or lifecycle/config events. Does not bypass missing aura access and does not drive the preferred secret-safe route. |
| C. Own bounded unit listener | Per-unit frames using verified `RegisterUnitEvent` reduce irrelevant unit work and permit explicit ownership/unregistration; up to 46 logical tokens (player, target, party1–4, raid1–40), with inactive sets omitted. More listener lifecycle and duplicated native aura processing. | Fallback only if a readable-data requirement cannot use A and a measured need warrants it. Never simultaneously scan the same scope through B and C. |
| Hybrid A + lifecycle dispatcher | Native slots evaluate presence; TwichUI dispatcher handles settings/profile, addon load, target, roster, capability and restriction recovery; provider unit-assignment observers rebind original containers. | Recommended design. An optional readable evaluator is a distinct mode with the restrictions in [detection](detection.md), not an automatic parallel second detector. |

The choices have different failure surfaces; these are source-based expectations, not measured results:

| Assessment | A: native containers via AuraKit | B: TwichUI dispatcher | C: owned bounded listeners |
|---|---|---|---|
| Reliability and completeness | Native engine owns aura deltas/assignment and handles secret data; complete only for predicates native filters can express. No generic exported aura callback or exact global winner is established. | Existing event plumbing is reliable for ordinary supported events; cannot recover forbidden aura payloads or validate eligibility by itself. | Narrow unit registration improves routing relevance, not data availability; assignment/discovery mistakes can lose updates. |
| Stability | AuraKit and provider discovery are inspected internals tied to the pin; Blizzard native filtering is the stronger semantic boundary. Isolate adapters by scope. | `R:On`/`R:Off` is owned project infrastructure; aura payload/API restrictions remain client-version dependent. | Uses client event API directly; TwichUI owns more registration/lifecycle code and compatibility work. |
| Delivery and ordering | Engine handles unit-scoped updates; provider assignment post-observer is still required. Do not assume ordering between two addons or recover state from slot visibility. | One callback receives payload after core dispatch; filter before work and coalesce by binding generation. No guaranteed provider-before-TwichUI event order. | Per-unit callbacks are narrow, but still no cross-frame/provider ordering guarantee. Revalidate live binding before paint. |
| Combat and secrecy | Source supports native filtering; slot subtree writes can be restricted independently of combat. Prebuild and defer structural/restyle work. No Lua secret arbitration. | Registering an event is no grant to inspect secret payloads. Protected attachment and query restrictions still apply. | Same restrictions as B; additional unit frames/listeners do not bypass them. |
| Capability/config updates | Use current capability/config gates, recompile own candidates and rebind. Capability callback exists only for offensive capability, not all friendly cases. | Straightforward explicit config/capability/target/roster refreshes, but full snapshots are access-dependent. | Must update the active registration set and invalidate every retired binding on the same changes. |
| Performance | Avoids duplicate Lua scanning; native slot count/filter count and per-binding construction still cost. Share one container's own slots per binding where feasible. Must measure raid bursts and idle work. | One global listener plus bounded membership filtering; shared snapshots can reduce duplicate displayed-unit work. Receives unrelated aura events. | Unit-filtered traffic reduces irrelevant callbacks, at the cost of extra listener objects and registration churn; worthwhile only with evidence. |
| Complexity | Predicate compiler, versioned frame discovery and restriction-aware initialization are the hard parts; avoid a second Lua detector. | Reuses event lifecycle but requires normalized cache/delta reconciliation and missing-data policy if readable evaluation is built. | Adds unit-frame registration ownership, deduplication and churn handling to B's evaluator complexity. |
| Failure and recovery | Missing API/changed provider disables affected scope; clear/rebind owned containers after a safe lifecycle edge. Retain rules. Restriction-lift restyles are generation-checked. | Access failure invalidates readable result; disable removes listener; next safe full refresh recovers without a timer loop. | Same fail-closed evaluation; unbind unregisters unit listener. Reconcile a bounded active set on roster/target/provider changes. |

Disabling clears/binds down original containers, unregisters owned listeners, cancels queued work, stops owned effects, and invalidates callbacks with a generation value. Permanent provider post-observers, if needed, install once and early-return when inactive. No permanent polling of all 40 raid units; one bounded deferred refresh after load/roster/layout changes is sufficient to rediscover candidates. Native containers do their own ordinary aura updates.

## Four scopes, roster and identity

The native container's `SetUnit` accepts a string token, and its `GetDynamicUnitEvents` registers `UNIT_AURA` against that current token. The inspected provider already binds player/target in Unit Frames and party/raid in Raid Frames. This establishes a source-supported route for all four scopes; it does not certify event delivery to addon Lua in restricted content. Player uses `player`; target follows `target` plus `PLAYER_TARGET_CHANGED`; displayed party buttons use `player`/`party1`–`party4`; displayed raid buttons use `raid1`–`raid40`. Bind from actual provider attributes rather than manufacturing all tokens as active bindings.

Forever [`UnitDocumentation.lua:1192`](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua#L1192) documents `UnitExists`; [`1637`](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua#L1637) documents `UnitInParty`; [`1683`](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua#L1683) documents `UnitInRaid` and marks it **secret when unit identity is restricted**. A raid index is not a safe persistent identity or unchecked Lua table key. `GROUP_ROSTER_UPDATE` is declared in [`PartyInfoDocumentation.lua:678`](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/PartyInfoDocumentation.lua#L678). Provider [`EUI_RaidFrames_Layout.lua:274`](https://github.com/EllesmereGaming/EllesmereUI/blob/8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5/EllesmereUIRaidFrames/EUI_RaidFrames_Layout.lua#L274) uses `GetNumGroupMembers()` to bound roster enumeration; a group count is an enumeration bound, not proof a specific displayed button belongs to a current occupant. No generated API entry for that global was found in the inspected source, so its availability is established here by actual provider usage rather than a guessed signature.

`UnitExists` guards lookup; roster/member APIs select plausible current scope; the provider's sanctioned unit attribute and binding generation identify where to render. No GUID is required for rule persistence. If a GUID is ever used as a transient change hint, check secrecy before equality or caching and discard it on ambiguity. Target/roster notifications trigger reconciliation, while provider attribute reassignment closes the timing gap they leave. `UNIT_FLAGS`/`UNIT_FACTION` invalidate friendly/offensive relationship; native candidate processing also watches them where needed. On map/visibility transitions, an unavailable aura query cannot establish absence; a unit can exist while its auras are inaccessible.

All provider namespace/maps/frame data above are **internal inspected interfaces**, not a provider compatibility contract. The party/raid adapter should fail closed independently from player/target if those interfaces change. Resolve the namespace only after provider load; assert feature shape and versions in diagnostics, never require the optional provider for TwichUI startup.

Raid Style's [`OnAttributeChanged("unit")` observer (1127)](https://github.com/EllesmereGaming/EllesmereUI/blob/8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5/EllesmereUIRaidFrames/EUI_RaidFrames_Style.lua#L1127) and `RFC_OnUnitAssigned` show why roster events alone are insufficient: secure headers can assign after a roster refresh, and can reassign the same token to another occupant. A TwichUI original observer must preserve existing scripts, clear its old binding immediately, re-read sanctioned attributes, and rebind even on same-token reassignment. No provider script replacement, unit attribute write, sort change or map mutation is permitted. If observing/binding is refused under restriction, clear the old owned display through its permitted lifecycle or keep it gated off until reconciliation; never retain a guessed occupant.

Health geometry can differ from the button: Unit Frames may clip under `_barClip`; party/raid uniform anchoring and kits have decorative proxy hosts. Validate the actual `StatusBar` and bounded ancestry; use `frame.Health` or `d.health`, not `d.uniformRef`, the whole clickable button or a full-frame anchor helper. Background wash/border/effect descendants remain TwichUI-owned. Preserve EUI text, absorb/shield, threat, target/hover and aura bands. Full health-rectangle effects use bar bounds; fill effects may anchor to `GetStatusBarTexture()` without reading secret health values. Axis/reverse/scale/layout changes require attachment reconciliation.

## Security and coexistence requirements

- Prepare structure/anchors out of combat on protected health-bar trees; late layout edits queue for `PLAYER_REGEN_ENABLED`. Native aura secrecy is an additional restriction independent of combat. Do not assume combat end permits restyling a secret aura subtree.
- Build slot descendants inside their `initializeFrame` creation window. EUI [`ApplyRFDispelSlot` (680)](https://github.com/EllesmereGaming/EllesmereUI/blob/8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5/EllesmereUIRaidFrames/EUI_RaidFrames_AuraContainers.lua#L680) reports slot-owned layout writes refused outside that window under secrecy. Queue appearance changes for a verified restriction lift; report pending settings state accurately.
- Never add `OnShow`/`OnHide` scripts or post-observers to engine aura buttons to count visible rules. EUI [`AuraContainers:1117`](https://github.com/EllesmereGaming/EllesmereUI/blob/8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5/EllesmereUIRaidFrames/EUI_RaidFrames_AuraContainers.lua#L1117) documents native secret-driven `SetShown` failing because of these handlers. No visibility side channel is an acceptable arbitration mechanism.
- Do not modify EUI's native dispel slots, Buff/Debuff Manager, aura filters, colors or saved options. F22 presents original opt-in decoration; explain possible overlap in the settings preview. Never silently disable an EUI effect.
- Missing/outdated optional provider, failed source lookup, forbidden object or unreadable relationship means no attachment/signal for that scope. This does not erase the player's rules. A preview uses synthetic state and never asserts that a live aura was recognized.

## Verification planned for implementation

Meaningful offline cases are provider-absent startup, verified versus wrong health fields, clipping ancestry, party versus raid visibility, reassigned/same-token occupants, target friendliness flips, disable/profile callback invalidation, bounded rules/slots and restriction-deferred restyling. Provider fixtures must reproduce actual shapes above and be labeled **unit-tested**, not provider-tested. Simulator pages/previews can test construction and settings navigation, but cannot prove native AuraContainer secrecy, combat taint, secure-header timing or effect appearance.

Optional owner-directed native validation should record exact Forever/EUI versions, verify attachment on player/target/party/raid health bars, test target and header reassignment, test restricted instances plus combat reload/deferred edits, and review overlap with EUI dispel, absorb, text and border options. These are disclosed uncertainties, not a requirement to alter a live install during this design task.
