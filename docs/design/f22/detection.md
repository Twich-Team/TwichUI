# F22 aura detection and capability semantics

Design research only. The source pins, provider attachment and recommended native propagation are in [integration](integration.md). All compatibility findings here are **source-verified**; runtime behavior is **not tested**. The central constraint is that a display can be native and secret-safe while the addon cannot read which aura caused it. A rule model must preserve that distinction.

## Relationship, aura kind and capability are separate

A friendly rule considers **harmful** auras on an assistable unit. An offensive rule considers **helpful** auras on a hostile/attackable unit. Re-evaluate when target, flags, faction, roster or unit assignment changes. Unknown/secret relationship suspends both lanes for that binding. A hostile debuff is not an offensive dispel opportunity; a friendly buff is not a friendly cleanse opportunity. Neutral/unattackable and mind-controlled units need current sanctioned relationship results, not a class or unit-token guess.

Each rule needs a capability mode, separate from the player selecting types:

- **Known capability:** require positive, current evidence that the player has a removal mechanism for that type and that the mechanism applies to this scope. The signal means “matching aura and known removal capability,” never “cast now.” Cooldown, resources, range, line of sight, school lockout and actual cast success are outside this contract.
- **Selected types:** show the selected native aura categories regardless of the player's abilities. This is a deliberate broader informational mode. It never upgrades capability or unknown data to eligible.
- **Unknown capability:** missing API, access failure, unsupported spell mapping, changed provider semantics or ambiguous knowledge yields unknown. In Known capability mode suppress that category, retain settings, and show an availability explanation in settings/diagnostics. An affirmative unavailable result also suppresses it, but is distinguishable for diagnosis.

A configuration whitelist chooses categories; it cannot prove the player learned a cleanse, turn Poison into a purgeable enemy buff, or make Bleed generally removable. If explicit “show unknown as informational” behavior is offered, it must be a Selected types rule with a distinct explanation, not a silent fallback of Known capability.

This matrix records what the inspected APIs establish, not a Retail class guide or a spell database.

EUI's actual helper is [`EllesmereUI_AuraKit.lua:2376–2465`](https://github.com/EllesmereGaming/EllesmereUI/blob/8abfcbf6afa4129369cdc9fb5e03e96d1fdd94e5/EllesmereUI_AuraKit.lua#L2376). It tests modern `C_SpellBook` APIs, player/pet banks and optional talents; refreshes on `SPELLS_CHANGED`, `UNIT_PET`, `TRAIT_CONFIG_UPDATED`, `PLAYER_ENTERING_WORLD`; and notifies only on capability flips. The spell list includes entries for classes outside TwichUI's Forever scope. Reusing its **current Boolean result** as provider capability evidence is different from copying its list and asserting Forever spell availability. A future independent capability provider needs versioned Forever evidence, rank/talent/pet handling, and failure-as-unknown. The design does not claim that complete provider already exists.

There is a material wording conflict: Forever `AuraUtil.lua:284` describes `RAID_PLAYER_DISPELLABLE` as auras **someone in the player's raid** can dispel, including enemy helpful enrages. EUI's friendly dispel source comments describe it as knowing the player's class/spec. The C-side implementation resolving that discrepancy was not available in the inspected UI source. Therefore the token by itself is not sufficient evidence for the product wording **“you can remove.”** Pair native category/predicate selection with independently verified current player capability; where that still cannot establish per-aura eligibility (especially offensive magic/steal), label the rule informational or suppress Known capability rather than overclaiming. `HARMFUL|RAID` is described in the same Forever table as harmful auras the player can dispel, but this too is source documentation, not proof of completeness for talents, pets or racials.

## What a rule can reliably express

| Requested predicate | Native restricted display | Readable Lua evaluator | Product behavior |
|---|---|---|---|
| Friendly Magic/Curse/Disease/Poison/Bleed presence | Supported by native type candidate sets, subject to binding and access rules. | Can evaluate when all required values are non-secret and access succeeds. | Selected types is feasible. Known capability adds the verified scope-specific capability gate above. |
| Offensive helpful dispellable or stealable presence | Native helpful filter plus appropriate dispel token / candidate exists; exact “you” semantics remain constrained. | Only if aura identity/type/flags and eligibility evidence are readable. | Keep purge and spellsteal choices distinct. No friendly-capability reuse. |
| Several selected types (OR) | A single native include-type set represents the union. | Ordinary set membership on checked strings. | Match any selected valid type, with deterministic color/visual policy independent of a secret aura name. |
| Exact friendly harmful spell whitelist | Usually identity-gated; non-never-secret spells rejected by include map. | Only where normal access exposes plain identity, and not as a workaround for native identity policy. | Mark unavailable in restricted contexts; no broad type fallback for an exact rule. |
| Exact hostile helpful spell whitelist | Same gate as above. | Same boundary. | Enemy purge/steal rules cannot promise arbitrary exact-spell tracking. |
| Spell exclusions on friendly harmful / hostile helpful auras | Ignored where identity matching is forbidden, except never-secret exemption. | Can honor only when access and normal policy permit. | **Required exclusion must never be silently ignored.** Suspend the rule in contexts where the exclusion cannot be guaranteed; retain the draft and explain why. |
| Maximum total duration | Native `maxDuration` exists, excludes permanent auras implicitly. | Check readable finite total duration. | This is maximum duration, not “expires within N seconds.” Do not mislabel it. |
| Remaining duration / stack threshold / caster identity / arbitrary conjunction | No general candidate contract established here; native controls exist for some separate display features, not an arbitrary predicate language. | Conditional on readable values and explicitly supported semantics. | Not guaranteed under secrecy. Hide an unsupported rule rather than drop predicates. |
| Per-aura exact priority and one cross-rule winner | Engine sort can choose one aura **inside a slot**. No verified callback exposes secret cross-slot occupancy. | Deterministic comparator possible with readable candidates only. | Restricted mode uses a declared compatible native visual policy or marks the rule combination unavailable. Never pretend slot assignment is a global rule comparator. |

`CanApplyIdentityCandidateFilters` deliberately disallows harmful-friendly and helpful-hostile identities even when addon authors wish to filter them. Never-secret spell exemptions are the only documented exception in this code. Native inclusion/exclusion maps are not a license to bypass that policy through raw Lua, tooltip text, exported regions or a second detector.

## Deterministic competition without a secret side channel

For readable candidates, apply eligibility and required exclusions first. Then select by: rule priority (higher first), stable rule order/ID, explicit type order, spell ID, then aura instance ID. Every comparator field must be non-secret and validated before use; do not sort on icon/name/expiration unless explicitly promised and checked. Multiple aura instances satisfying the same rule produce one effect; removal of the winner selects the next eligible candidate. Profile or binding changes discard all previous candidates. Exclusions win over inclusions, and a failed required predicate never partially matches.

For native secret-safe slots, compile supported rules into disjoint predicates when the vocabulary permits (type partitions, token negation, complementary booleans). This prevents the same aura from being owned by several rules, but **does not** by itself prevent different matching auras from activating several slots. Exact exclusive winner selection across arbitrary rules is unproven. A static layer order can establish visual precedence, as EUI's Magic/Curse/etc overlay sublevels do, but translucent layers may blend and lower effects may keep running. Describe that as fixed visual precedence, not as “only the highest rule runs.” Do not read `IsShown`, register visibility handlers or inspect animation progress to recover secret presence.

The first implementation should choose one explicit contract: support independently composable native lanes with fixed precedence, or restrict a binding to one native rule while offering richer arbitration only in readable mode. Which product contract is chosen belongs in [rules](rules.md); it cannot be solved by merely adding a dispatcher. Any requirement for exactly one arbitrary winning rule under secrecy remains an implementation feasibility gate.

## Readable-mode lifecycle, if separately implemented

Use exactly one owned aura-event route (TwichUI dispatcher or bounded listeners), watch only enabled bound units, and avoid a recurring scan. First binding / full update rebuilds from a bounded snapshot; deltas remove checked IDs, add checked auras, and fetch checked updated IDs. Check access and `issecretvalue` **before** comparisons, map indexing, sorting, string formatting or logging, including container values and IDs. A failed fetch, malformed delta or restricted transition invalidates the current result; do not retain the last eligible effect. Ambiguous/incomplete bounded scans are unknown, never “no aura” or “safe to display.” A cap hit either uses a verified complete snapshot mechanism or suppresses that evaluation.

Keep active rule/unit/slot counts explicit and bounded in the implementation plan. Deduplicate aura work across multiple displayed bindings for the same logical unit when using readable mode; native consumers remain per actual frame. No SavedVariables aura cache, historical identity log, automatic cast, secure-click modification, chat alert or gameplay action follows from a match. Disable/profile change/unbind cancels pending evaluations and clears owned effects immediately through permitted lifecycle operations.

## Concrete cases to validate

1. Friendly poison on a party health bar, with Selected types Poison: native category presence may draw the configured wash even on a mage. Changing to Known capability suppresses it for a character with positively known lack of friendly poison removal; an unknown mapping also suppresses with a distinct availability explanation. A known self-only racial never enables the party rule.
2. Enemy target helpful Magic, offensive rule: a known purge capability plus native permitted eligibility can signal a purge candidate; a “stealable only” variant additionally requires stealability and known Spellsteal capability. A friendly Magic cleanse spell alone must not enable this rule. Exact spell exclusions unavailable under the hostile-helpful identity gate suspend the rule instead of being ignored.
3. Player Bleed plus friendly Magic at once: Bleed is eligible in Known capability only with verified current self-removal evidence. A chosen native fixed precedence policy must render deterministically without reading slot visibility. If the saved rule demands one exact global winner and unsupported secret identity/exclusions, show no unsupported result; do not choose whichever aura event ran last.

These are prospective validation scenarios, not executed tests. Additional coverage needs include class/talent/pet changes, stale provider helpers, rank changes, aura refresh/removal, competing instances, target reaction change, same-token header reassignment, native identity-gate behavior, and restrictions beginning between query and evaluation.
