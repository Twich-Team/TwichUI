# F16: Healer Watch communication discovery

**Status: investigated; implementation blocked pending client interaction and outbound-chat evidence.** The requested hover-and-click action is not implemented. No messages are sent by this work, and the live monitor remains unchanged. This is a bounded alternative for owner review, not an approved new interface.

## Current interaction and evidence

- [`healer/Display.lua`](../!!!TwichUI/healer/Display.lua) creates the live panel with mouse disabled. Its `pick` button takes the mouse only when the live view has a problem such as **Choose a healer**; it opens the existing healer-selection menu. The positioning handle takes input only while moving. Once a healer is watched, the panel is click-through. The on-screen preview is a separate state; it must never become a sender.
- [`healer/Picker.lua`](../!!!TwichUI/healer/Picker.lua) is a pooled, explicit-click menu for choosing the watched unit. Its selection is not evidence of the player's own state. [`healer/Watch.lua`](../!!!TwichUI/healer/Watch.lua) monitors a chosen healer and can display measured mana, aura-confirmed drinking or that person's received chat, each with restricted/unknown states. The watch target is not necessarily the player. Do not turn a watched healer's observations into a statement spoken by the player.
- [`SettingsBrokerMenu.lua`](../!!!TwichUI/modules/SettingsBrokerMenu.lua) is an existing independently clickable TwichUI data-bar menu, but it has no Healer Watch communication entry, and a data bar is an optional integration. It does not currently provide hover over the Healer Watch indicator. Reusing it would be a discoverable fallback for data-bar users, not proof that the requested panel hover is possible.
- `../wow-ui-source` and an installed Forever client source tree are absent locally. A bounded public-source check found the `forever` branch of Gethe/wow-ui-source at commit [`734f065329cff4992835b01a84f210a297db91b6`](https://github.com/Gethe/wow-ui-source/tree/734f065329cff4992835b01a84f210a297db91b6). Its generated [`ChatInfoDocumentation.lua`](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua) describes `C_ChatInfo.SendChatMessage` with `HasRestrictions` and `RestrictedForMacroChatMessages`, and no documented success return. `C_ChatInfo.InChatMessagingLockdown` reports when chat API security restrictions are active. This establishes API names and restriction metadata for that source revision, not that an addon callback can send in a particular Forever build, combat, dungeon or raid, nor that a call delivered a message. Incoming chat's secret-value restriction documented in [Healer Watch](healer-watch.md) is not evidence that outgoing chat is permitted.
- Existing group distribution conventions in [`pins/Ping.lua`](../!!!TwichUI/pins/Ping.lua) and [`npcs/Share.lua`](../!!!TwichUI/npcs/Share.lua) choose instance group, raid or party for **addon messages**. They are useful routing precedent, not proof that player chat accepts the same paths in every context. Solo has no group channel. No first-party Healer Watch outgoing-chat implementation currently exists.

Turning mouse input on for the live panel would change an explicitly documented click-through guarantee and could intercept gameplay. The current selection overlay is not an appropriate general hover surface: its intended state is a missing healer and its click already has another meaning. The existence of a mouse-motion API alone would not establish safe coexistence with clicks or other overlapping frames in Forever.

## Proposed safe interaction for review

Offer an **explicitly enabled, separate small communication handle** beside the panel, leaving the panel and its existing healer-picker/move behavior untouched. The handle would expose a small menu on hover and keep it open while moving to the choices; only clicking a named choice would attempt a single send. It must not cover or capture the normal watch panel, and hide or disable itself during preview/move and any unverified combat state. Position, discoverability and whether an optional data-bar entry should also open the same menu require owner review. If a separate handle is not acceptable or pointer coexistence cannot be established, provide a data-bar entry as an explicit alternative rather than changing the panel. The broker alternative alone does not fulfill the original hover-on-indicator interaction.

Choices are player-authored declarations, for example **“Drinking.”**, **“Out of mana.”**, **“Need a moment.”** and **“Ready.”** They describe the sender's own intent/state only, not the watched healer, group readiness or a recommended action. The player selects the message deliberately; neither hovering, opening a menu, a watch update, an alert nor an observation sends anything. Do not infer or auto-select a message from the watched unit. No whispers, timers, retries, queued sends, repeated messages or recurring polling.

At the moment of selection, recheck group membership and the actual supported chat destination. Prefer the player's active instance group if the verified client supports it, otherwise the verified raid or party channel; if solo, group state is ambiguous, the API is missing/restricted, or a safe click is unavailable, disable/refuse with a plain local explanation. Do not silently choose `/say` or another audience. Recheck again at click time rather than trusting a menu opened before a group change. A call with no documented success result must not be presented as confirmed delivery. Keep any refusal local and do not synthesize a success message.

## Evidence needed before coding

1. Match the target Forever build to its generated chat documentation and inspect the native chat send path and the meaning of `HasRestrictions` / `RestrictedForMacroChatMessages`, including secure/tainted addon handlers. Establish whether a direct, hardware-origin click on an addon-created button can send a fixed group message, and how denial is reported; do not bypass a restriction.
2. Verify party, raid and instance-group membership/destination behavior, including simultaneous home/instance groups, leaving/changing groups while a menu is open, solo and unavailable APIs. Verify combat and communication-lockdown behavior in the actual supported client; if unsafe or unknown, disable the action clearly rather than guessing.
3. Verify an opt-in handle's pointer hitbox beside the live panel does not intercept normal gameplay or the existing **Choose a healer** picker and move handle. Check enter/leave transition to the menu, click-away, Escape, scale, anchor and screen-edge behavior. If that cannot be done, retain the click-through display and use a separately approved entry point.
4. With a controlled group and owner-directed client test, confirm hover/open never sends; each click causes at most one intended self-status message on the expected channel; solo/restricted/invalidated contexts send none; no misleading delivery confirmation appears. Check feature disable, preview, combat and profile changes cancel or close stale UI. Confirm watching another healer never changes message subject and that monitoring, alerts and visibility remain unchanged.

**Evidence label:** source-inspected, including the linked public generated documentation revision. The local Forever source, simulator and real client were not available for this review. No UI, chat or gameplay test was run; no existing code or settings were changed.
